## 1. The bet

The Dispatcher's between-sessions logistics is a state machine over files, and the Guild already writes every file it needs. Judgment lives IN sessions (Architect, Builder, Digger); nothing between sessions requires a model. Mechanize the between, keep the mantles, and Felix's attention narrows to what is genuinely his: gates, escalations, taste. **Goal, his words: maximize time between Felix-gates.**

## 2. The audit — what a Dispatcher does, tested for judgment

1. Compose kickoffs → **mechanical** (fenced verbatim in orders + rider; the rail already resolves them).
2. Fire on dependency-LANDED → **mechanical** (board parse per D63 + census).
3. Bulletin relay → **mechanical** copy; obsolete on serial-master batches.
4. Hold on escalation/kill/block → the only judgment, and its mechanized form is **pause and surface** — D10's move, not a decision.
5. Staff the judge on an escalated landing → **mechanical** (fire the scoped Architect sitting; the judgment is the sitting's, staffing it never was) — see §5.1, the reactive gate.

## 3. The flow object — the batch note as data

A **flow** is a declared DAG of steps. A step is a row id carrying: kickoff (resolved from the order's fence), account, tier (from Staffing), venue (master | worktree + branch), dependencies, permission mode (§5), and gate markers — a Felix-card, or an **Architect sitting, itself a fireable step**, so review rides the string. Storage format rides canon row 17 (the storage experiment, D7's AI-native mandate) — this is a schema question, not markdown-prose parsing round 2.

## 4. The contract — D11

**The DAG is drawn, not listed (Felix, this sitting).** The flow page renders the graph itself: nodes = steps (encapsulation-first labels, mantle colours, status rings — the City View's vocabulary), edges = dependencies, parallel lanes side by side, gates inline as Felix-cards, and the live census lights each node as it runs — plan view and progress view are the same drawing. The same renderer can later draw a board's Depends-on graph on building pages (parked, post-v0).

One click arms the flow; **the review of the rendered DAG is the authorization.** The engine fires only declared steps through the existing hands (no new write class — the fence stands), pauses at Felix-cards, on any ambiguity (**D10 binds the engine wholesale**), and on HALT (its first consumer). Armed flows are immutable: the Architect amends the flow file and unfired amended steps re-arm with one click — which dissolves D57's relay dance. The arm view shows the bill: tier per step, usage per account (B5's strip feeds it) — "a one-click dispatcher that hides the bill is how a sovereign DoS's himself" (founding line).

**Dynamic extension (Felix's word at the B9 close: "reactive, dynamic flow").** The DAG is not fixed at arm time — judge sittings and gate Architects cut new rows mid-flow, and the engine re-reads the plan (files carry truth), so the string grows while it runs. What authorizes grown steps is the chapter's first **Felix-fork, pre-ruled at the cut sitting's blessing**: **step-arm** (every extension re-arms — one Felix click per batch boundary) vs **scope-arm** (the arm covers a declared scope — building + chapter — and judge-cut rows inside it auto-join; Felix-cards and HALT still stop everything). Felix leans scope-arm — the continuous flow is the commission — but the ruling waits for the blessing. **(Ruled 2026-08-27 at the batch-5 blessing: scope-arm — D12, his word.)**

## 5. The physics, named — the chapter's probe questions

1. **LANDED lies by omission.** B3 landed with two escalations pausing the chain; a naive engine fires over them. Interim law: strict-parse the landing, anything malformed or escalation-marked → pause + card (pausing is cheap, wrong continuation is expensive). Real fix: a machine-readable `holds` on the landing grammar — §6. **And the pause does not card Felix — it fires the judge (the reactive gate; Felix's ask, B5 sitting):** an escalation-marked landing auto-fires the scoped Architect sitting into the lane — the DAG draws the inserted judge node — and the lane resumes when the sitting lands with holds cleared; Felix's card appears only when that Architect escalates to *him*. B6's apply button is this mechanism's v0 prototype. The campaign is the evidence: five build rows, seven escalations, **six Architect-delegated** — Felix hand-relayed every ruling — while B8's fully-pre-chewed order escalated **zero**. Both facts point the same way: pre-chew what you can, staff the judge for the rest, card the sovereign only for what is his.
2. **S5 — spawned sessions stall in manual mode** at the first tool call (P2, parked), despite `defaultMode: auto` on the account. Measure the mechanism (cmux `--settings` injection?); permission mode becomes part of the step spec, and the posture per venue is Felix's. Evidence to date: B6's apply probe and B7's three fires all started, beat, and landed transcripts — but none proves **sustained unattended tool work**. S5 is probe #1 and its kill criterion shapes the chapter. *(Upgraded 2026-08-27, the flow-cut sitting — its own session is the positive control: fired from `/summon`, census `mode:auto` on every beat, dozens of unattended tool calls to completion in a trusted root on the personal account. The stall is conditional, not universal; P5 probes the failing cells and the mechanism — [p5-permission-physics.md](p5-permission-physics.md).)*
3. **Concurrency lanes:** the flow file carries what batch notes carry — serial lanes on shared checkouts, parallel lanes in worktrees (the hands compose them today).
4. **Liveness:** census `Stop` + `kill -0` (P1's two-sensor law, proven); step timeouts — everything has a limit.
